Rauthy Documentation

LDAP

Some apps can only check a username and password against a directory with an LDAP bind, for instance the native Jellyfin apps through the Jellyfin LDAP plugin. Rauthy can serve these apps directly with a minimal, read-only LDAPS server, so you don’t need a second user directory next to it.

It is disabled by default. Enable it in the [ldap] section:

[ldap]
enable = true
port = 6360
base_dn = 'dc=example,dc=com'
# optional, defaults to the `[tls]` certificate
#cert_path = 'tls/ldap.crt'
#key_path = 'tls/ldap.key'

Only implicit TLS (LDAPS) is supported, StartTLS is not. If Rauthy itself runs plain HTTP behind a reverse proxy, set cert_path and key_path, unless the proxy terminates TLS for LDAP as well.

If your reverse proxy forwards the raw TCP stream and terminates TLS itself, set ldap.plain_text = true to serve plain LDAP. As a safeguard, this requires server.proxy_mode = true. Rauthy then sees the proxy’s IP for every LDAP connection, so the per-IP brute-force protection below applies to the proxy as a whole. Never expose the plain LDAP port to anything but the proxy.

Supported Operations

Simple bind, search, unbind, the RootDSE and Who Am I (RFC 4532). Every other operation returns unwillingToPerform. Search filters support and, or, not, equality, presence and substring.

Clients

Each LDAP app is a Rauthy client with the password flow enabled. Binds and searches are scoped to this client, and every client gets its own subtree:

cn=<client_id>,ou=clients,<base_dn>                        the app's bind DN and base DN
uid=<uid>,ou=people,cn=<client_id>,ou=clients,<base_dn>    users
cn=<group>,ou=groups,cn=<client_id>,ou=clients,<base_dn>   groups
  • Service bind: the app binds as cn=<client_id>,ou=clients,<base_dn> with the client secret. This requires a confidential client.
  • User bind: a user binds as uid=<uid>,ou=people,cn=<client_id>,ou=clients,<base_dn> with their password. This runs the same checks as the password grant: brute-force prevention and login delays, credential stuffing detection, enabled / expired users and the client’s group restriction (restrict_group_prefix). A user bind can only search its own entry, the whole directory is only visible to the service bind.

Like the password grant, a confidential client needs its secret for user logins as well. For a confidential client, a user bind only succeeds on a connection that already did a successful service bind for the same client. Apps like the Jellyfin LDAP plugin do exactly this: they bind as the service, search the user, and then bind as the user on the same connection. A public client accepts user binds right away.

Each successful user bind creates an LdapLogin event, with events.level_ldap_login as its level. At most ldap.max_connections (default 1000) connections are open at the same time, further ones wait until one is closed.

All users of an app bind from the app’s IP. By default, a few failed user binds with different usernames therefore trigger the credential stuffing detection and block the app’s IP for everyone. If the LDAPS port is only reachable for your apps, you can set ldap.disable_ip_brute_force_protection = true. User binds then skip all per-IP checks and only the per-user failed login counter slows down repeated failures.

Like the password grant, LDAP binds cannot do MFA. A user with MFA or passkeys who also has a local password can log in with the password alone. Only users with a local password can log in, passkey-only or upstream-provider-only accounts are not part of the directory.

Connections are closed after 5 minutes idle and after 1 hour at most, so a rotated client secret applies to open connections within that time.

Below server.ssp_threshold users (default 1000), each search loads the whole directory. At or above it, a search only loads the users it can return: a user bind’s own entry, the user of a search base like uid=alice,ou=people,..., or the users named in uid or mail equality filters, for instance (&(objectClass=inetOrgPerson)(uid=alice)) or (|(uid=alice)(mail=alice@example.com)), at most 50 different ones. Group entries then only list these users as members. Any other search from a service bind, like listing all users or groups, fails with sizeLimitExceeded.

Directory Layout

The layout follows LLDAP, so existing app presets only need a different base DN.

Users (ou=people) are all users allowed for the client that have a local password and a PAM username, and are enabled and not expired. The PAM username is the uid. LDAP compares uids case-insensitively, and PAM usernames are always lowercase, so they are the only names that are guaranteed to be unique. Each user who should log in via LDAP therefore needs a PAM user. Users without one are not part of the directory and cannot bind:

attributevalue
uidPAM username
entryUUIDthe Rauthy user ID
mailemail
cn, displayNamegiven name + family name
givenName, sngiven name, family name
memberOfthe DNs of the user’s groups

Groups (ou=groups) are Rauthy groups, filtered by the client’s restrict_group_prefix if set, with cn and member / uniqueMember.

Example: Jellyfin LDAP Plugin

Create a confidential client jellyfin with the password flow enabled, optionally with a group prefix like jellyfin, and configure the plugin with:

settingvalue
LDAP Server / Portyour Rauthy host / 6360
Secure LDAPenabled
LDAP Bind Usercn=jellyfin,ou=clients,dc=example,dc=com
LDAP Bind User Passwordthe client secret
LDAP Base DN for searchescn=jellyfin,ou=clients,dc=example,dc=com
LDAP Search Filter(objectClass=inetOrgPerson)
LDAP Search Attributesuid, mail
LDAP Uid AttributeentryUUID
LDAP Username Attributeuid
LDAP Admin Filter(memberOf=cn=jellyfin_admins,ou=groups,cn=jellyfin,ou=clients,dc=example,dc=com)

You can test a setup with the OpenLDAP tools:

ldapwhoami -H ldaps://rauthy.example.com:6360 \
  -D 'cn=jellyfin,ou=clients,dc=example,dc=com' -w '<client secret>'
ldapsearch -H ldaps://rauthy.example.com:6360 \
  -D 'cn=jellyfin,ou=clients,dc=example,dc=com' -w '<client secret>' \
  -b 'cn=jellyfin,ou=clients,dc=example,dc=com' '(uid=alice)'
